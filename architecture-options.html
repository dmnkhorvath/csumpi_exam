1 A Question rendering module high leverage

Files
src/pages/AllQuestionsPage.jsx:103–149 src/pages/CategoryPage.jsx:119–169 src/pages/SimilarityGroupsPage.jsx:129–145
Problem
“Question” is a first-class domain concept but has no module. It's reassembled inline on three pages — markdown body, options list, answer-reveal toggle, success-tinted answer block. Same interface (“show a question, hide/reveal its answer”), copy-pasted implementation. Markdown rendering setup and the revealedAnswers[key] toggle pattern are duplicated verbatim across all three.
Solution
One module that renders a Question with its reveal state. The three pages stop knowing about question_text, options, correct_answer field shapes.
Benefits
  • Locality: styling, a11y, a “repetitions” badge — all change in one file.
  • Leverage: three pages shrink to list/filter glue.
  • Real seam, not hypothetical: three concrete callers exist today.
  • Test surface: render against fixture Questions, assert reveal behaviour. Today: requires mounting whole pages.

2 An exam-data loading module high leverage

Files
src/pages/AllQuestionsPage.jsx:13–24 src/pages/CategoryPage.jsx:19–34 src/pages/SimilarityGroupsPage.jsx:14–52
Problem
Every page knows JSON URLs, fetch semantics, and the post-fetch transform. SimilarityGroupsPage goes further: it loops every category file and reconstructs similarity groups by bucketing on group id (:17–40) — that's domain logic about what a SimilarityGroup is, living in a useEffect.

Deletion test: remove that useEffect and the SimilarityGroup concept disappears from the codebase. Strong signal it wants a home.
Solution
A module that owns “load all questions”, “load category X”, “load similarity groups”. Hides URLs, caching, and the bucketing transform. Pages receive already-shaped domain values.
Benefits
  • Locality: when on-disk JSON shape changes (or moves behind an API), one file changes.
  • Leverage: pages stop owning loading/error state for the same kind of data three times.
  • Test surface: the bucketing-into-SimilarityGroups transform becomes a pure function with fixtures, instead of being entangled with fetch + useState.

3 A SimilarityGroup module — the “canonical question” rule medium

Files
src/pages/CategoryPage.jsx:120–125 src/pages/SimilarityGroupsPage.jsx:44–46
Problem
The rule for which member of a similarity group represents it (“longest question with non-empty answer, else longest overall”), and the rule for which groups are interesting (size > 1), are domain decisions scattered inline next to JSX. Two pages reimplement adjacent slices of the same idea.
Solution
A module representing a SimilarityGroup with the “canonical member” and “is interesting” rules behind it.
Benefits
  • Small but deep: rules are trivial today, but exactly the kind that drift (e.g. future “prefer most-recent exam year”).
  • Locality: one place owns “what does it mean to be a similarity group”.
  • Test surface: the selection rule is a one-line pure function once it has a home.
  • Natural by-product of #2 — nice to do together.

4 helpers/categories.js — deepen, or accept as a constant judgment call

Files
src/helpers/categories.js (consumed by HomePage.jsx, CategoryPage.jsx, SimilarityGroupsPage.jsx)
Problem
Barely a module — a 14-line constant map. Deletion test is interesting: if we delete it, complexity does not concentrate; callers would hardcode 11 strings. That's the signature of shallow but harmless — a constant pretending to be a module.
Solution
Either:
  • (a) Extend into a real Category module owning lookups by name/file, canonical iteration order, and similarity-file paths (today computed in SimilarityGroupsPage.jsx:17–18); or
  • (b) Accept it as a constant and stop calling it a “helper”.
Lean (a) only if we do #2 and category→file mapping wants a single home anyway.
Benefits
Mostly informational — flagged so we don't deepen something that doesn't want depth.
